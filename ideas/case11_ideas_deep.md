# Case 11: Lunar Landing Site Navigator — 深掘り10案（着陸地点 × 探査ルートの統合と自動選定）

> **深掘りの軸（ユーザー方針）**
> - 地形・日照・通信を NASA データで一元的に可視化し、最適な**着陸地点と探査ルート**の選定を自動化する → 計画工数の削減、意思決定の効率化（ROI）
> - **移動効率・地形リスク・科学的価値**を同時に比較し、**なぜそのルートが選ばれたのか**を説明する
> - **機械学習よりも、NASA の実データを使った経路計算と分かりやすい可視化を優先**する
>
> 既存の [case11_ideas.md](case11_ideas.md) / [case12_ideas.md](case12_ideas.md) の10案（比較ボード、パノラマ、電力計算、延期カレンダー、適性マップなど）とは重ならないよう、**着陸後のルート**と**選定理由の説明**に重心を置いています。

## 共通の計算基盤（全案で使い回す）

各案はこの基盤の上に乗るので、**最初にここを作れば残りは画面を足すだけ**になります。

| 層 | 中身 | NASA データ |
|---|---|---|
| 地形 | 標高、傾斜、粗さ（起伏） | **LOLA 南極 DEM**（例: 20 m/pixel、PDS / PGDA） |
| 日照 | 平均日照率、指定日時の影 | **LOLA ベースの南極日照マップ**（NASA Goddard PGDA）、DEM からの地平線計算 |
| 通信 | 地球の可視率、指定日時に地球が見えるか | PGDA の地球可視マップ、**JPL Horizons**（月面座標から見た地球の方位・高度） |
| 太陽・地球の位置 | 指定日時の方位・高度 | **JPL Horizons API**（観測地点を月面の座標で指定） |
| 科学的価値 | 永久影（PSR）への近さ、氷が安定しやすい温度、水素の多さ | **LROC の PSR 範囲**、**LRO Diviner**（温度）、**LRO LEND**（中性子 = 水素の指標） |

**経路計算**: グリッド上の A*（またはダイクストラ）。1マスあたりのコストは次の式で、重みと各項の定義は画面に表示します（ブラックボックスにしない）。

```
コスト = w1 × 移動効率（距離 + 傾斜による登坂負荷）
       + w2 × 地形リスク（傾斜・粗さ・影の中を走る時間）
       − w3 × 科学的価値（目標の近くを通るほど減る）
通行不可: 傾斜が上限（例: 20°）を超えるマス
```

**実装方針**: 重い処理（DEM の切り出し、傾斜計算、地平線計算）は Python（rasterio / numpy）で事前に計算し、PNG と JSON に書き出す。フロントは表示とインタラクションに集中する。対象範囲は**1地域・約10 km × 10 km**（20 m 解像度で 500 × 500 マス）に絞れば、A* はブラウザでも一瞬で終わる。

## 案1: Explainable Traverse Planner — 3軸のコストで経路を計算し、区間ごとに「なぜこの道か」を説明

- **コンセプト**: 着陸地点と目標（例: 永久影クレーターの縁）を選ぶと、A* で経路を計算する。**地図上の各区間をクリックすると**、「ここは傾斜が8°で緩い」「この迂回で影の中の走行を40分減らした」など、その区間を選んだ理由が出る。
- **自動化するもの**: ルートの探索と、その根拠の説明
- **主な機能**: 経路の描画、区間ごとのコスト内訳（3軸の積み上げバー）、ルート全体の要約（距離・最大傾斜・影の時間・訪れる科学目標）
- **技術**: Python で事前計算 → React + Leaflet（または deck.gl）で表示、A* は JS で実装
- **ROI**: 「この道で本当にいいのか」を確認する会議の時間を短くできる
- **1日MVP**: 1地域、着陸地点3つ × 目標3つ、区間の理由テキストはテンプレートで生成
- **リスク**: 説明文は計算結果から機械的に作る（LLM で作文しない）。数値と文章がずれないようにする

## 案2: Route Comparison Board — 「最短 / 最安全 / 科学最大」の3ルートを並べて比べる

- **コンセプト**: 重みを3通りに変えて計算した3本のルートを、同じ地図に重ねて表示する。横にレーダーチャート（移動効率・地形リスク・科学的価値）と**標高・傾斜の縦断図**を並べ、「科学最大ルートは2 km 長いが、氷の可能性が高い地点を2つ通る」とトレードオフを一目で示す。
- **自動化するもの**: 代替案の生成と、その比較
- **主な機能**: 3ルートの色分け表示、レーダーチャート、縦断図、推奨ルートと推奨理由の表示
- **技術**: React + Recharts、案1のエンジンを流用
- **ROI**: 代替案を手作業で作って比べる工数がなくなる
- **1日MVP**: 3ルート × レーダーチャート × 縦断図
- **リスク**: 3本がほぼ同じ道になると比較にならない。デモ用には差が出る地域を選んでおく
- **一押し**: 「同時に比較し、なぜ選ばれたかを説明」という要望を、最もそのまま形にできる

## 案3: Land-for-the-Route — ルートまで含めて着陸地点を選ぶ

- **コンセプト**: 普通は「着陸地点を決めてから道を考える」が、この案では**目標までのルートの良し悪しを含めて着陸地点を評価**する。候補地点ごとに目標までのルートを自動計算し、「着陸条件は2位だが、ルート込みでは1位」という逆転を見せる。
- **自動化するもの**: 着陸地点のランキング（ルートのコスト込み）
- **主な機能**: 候補地点のランキング表（着陸条件のスコア + ルートのスコア）、順位が入れ替わった理由の説明
- **使用データ**: 共通基盤 + 着陸楕円内の傾斜
- **ROI**: 着陸地点の検討とルートの検討を一度に行える。部署間の行き来が減る
- **1日MVP**: 候補地点5つ × 目標1つ
- **リスク**: **Case 11 の本題（着陸地点・日付の比較）とルート計画をつなぐ案**なので、審査の「課題への適合」を守るうえで重要

## 案4: Sun & Earth Along the Route — 出発日時を変えると、ルート上で太陽と地球が見えるかが変わる

- **コンセプト**: Case 11 の核心である**太陽と地球の位置**をルートに持ち込む。出発日時のスライダーを動かすと、ルート上の各地点が「日が当たっている / 影」「地球が見える / 見えない」で色分けされる。「この日に出発すると、後半3 km は影の中で通信もできない」が一目でわかる。
- **自動化するもの**: 出発日時ごとの日照・通信の判定
- **主な機能**: ルートの色分け、時間軸のタイムライン（日照・通信の帯）、日時スライダー、選んだ地点の地平線と太陽・地球の位置
- **使用データ**: **JPL Horizons**（太陽・地球の方位・高度）+ DEM から計算した各地点の地平線
- **技術**: Python で途中地点（例: 200 m ごと）の地平線を事前計算 → フロントで太陽・地球の高度と比べる
- **ROI**: 日程が変わったときの再確認が一瞬で終わる
- **1日MVP**: ルート1本 × 途中地点20か所 × 14日分（1時間刻み）
- **リスク**: 地平線の計算が一番重い。地点数を絞り、事前計算に時間を確保しておく

## 案5: Why-Not Explorer — 自分で描いたルートと自動ルートの差を説明する

- **コンセプト**: 計画担当者が「こっちの谷を通った方がいいのでは？」と思ったら、地図上で経由地を足して自分のルートを作れる。すると、**自動ルートとの差を3軸で表示し、なぜ自動ルートがそこを避けたのか**を説明する（「この谷は傾斜が22°で通行不可マスを含む」）。
- **自動化するもの**: 人の案と自動案の比較と、その説明
- **主な機能**: 経由地のドラッグ、2本のルートの差分表示、避けた理由のハイライト
- **ROI**: 専門家の直感と計算結果のすり合わせが速くなる。自動化への信頼にもつながる
- **1日MVP**: 経由地1点の追加 → 再計算 → 差分表示
- **リスク**: UI の作り込みが必要。案1・案2の後に余力があれば

## 案6: Weight Tuner & Trade-off Frontier — 重みを動かすとルートがどう変わるかを見せる

- **コンセプト**: 「安全重視」「科学重視」のスライダーを動かすと、ルートがリアルタイムに変わる。さらに、たくさんの重みで計算した結果を**散布図（リスク × 科学的価値）**に並べ、「これ以上どちらも良くできない線（パレート前線）」を示す。科学チームと工学チームの落としどころを探すのに使える。
- **自動化するもの**: トレードオフの可視化
- **主な機能**: 重みのスライダー、ルートのリアルタイム更新、パレート前線の散布図
- **ROI**: 科学チームと工学チームの調整（課題文にある背景）を速くできる
- **1日MVP**: スライダー2本 + 散布図（事前に50通り計算）
- **リスク**: case12 の案3（交渉ボード）と考え方が近い。こちらは**ルートに特化**して差別化する

## 案7: Terrain Risk Layer Stack — 傾斜・粗さ・影・温度を重ね、通れる場所を自動で塗る

- **コンセプト**: 地図に傾斜・粗さ・平均日照・温度・PSR のレイヤーを重ね、ON/OFF できる。しきい値を決めると**通行可能マスク**が自動で作られ、ルート計算の土台になる。他の案すべての「見える化の土台」。
- **自動化するもの**: 通行可能エリアの判定
- **主な機能**: レイヤーの切り替え、しきい値のスライダー、凡例と出典の表示
- **使用データ**: LOLA DEM（傾斜・粗さ）、PGDA 日照マップ、Diviner（温度）、LROC PSR
- **ROI**: 複数のツール（Quickmap、Moon Trek など）を行き来する手間がなくなる
- **1日MVP**: 4レイヤー + しきい値1本
- **リスク**: これ単体では「地図ビューア」で終わる。**必ず案1か案2と組み合わせる**

## 案8: Science Stop Sequencer — 複数の科学目標を巡る順番を、電力・時間の制約つきで自動で決める

- **コンセプト**: 目標が複数ある場合（PSR の縁、水素の多い地点、露頭など）、**どの順番で回るか**を自動で決める。各地点での滞在時間、バッテリー、日照（充電できる時間）を制約に入れ、「この順なら日没までに全部回れる」を示す。
- **自動化するもの**: 巡回順序と滞在時間の計画
- **主な機能**: 巡回順の地図表示、ガントチャート（移動・観測・充電）、制約違反の警告
- **技術**: 目標数が少ない（5か所程度）ので、全順列を試すだけで十分（高度な最適化は不要）
- **ROI**: 運用計画の作成工数を減らせる
- **1日MVP**: 目標4か所 × 電力の簡易モデル
- **リスク**: 電力モデルを凝りすぎない。「太陽高度が低いと発電が減る」程度の簡易式で十分

## 案9: Slip Re-Route — 着陸日が延期されたら、ルートと滞在計画を自動で組み直す

- **コンセプト**: 課題文で強調されている「日程の変更」にルートで答える。着陸日を変えると、日照と通信の条件が変わるため、**ルートと各地点の滞在時間を自動で再計算**し、元の計画との差を説明する（「延期で区間3が影に入るため、北側に迂回 +600 m」）。
- **自動化するもの**: 日程変更後の再計画と、差分の説明
- **主な機能**: 元の計画と新しい計画の重ね合わせ、差分の一覧、影響の大きさ（色）
- **ROI**: 延期のたびに発生する再計画の工数を大きく減らせる。**ROI を最も具体的に語れる案**
- **1日MVP**: 延期パターン3つ（+7日、+14日、+29日）の再計算と差分表示
- **リスク**: 案4（時間ごとの日照・通信）が前提。順番として後回しにする

## 案10: Traverse Briefing Sheet — 選ばれたルートの「説明書」を自動で作る

- **コンセプト**: 意思決定の最後に必要なのは、関係者に配る資料。選んだルートについて、**区間表（距離・傾斜・日照・通信）、リスク、推奨理由、使ったデータの出典**を1枚にまとめて自動生成する。
- **自動化するもの**: 説明資料の作成
- **主な機能**: 区間表、地図のスナップショット、出典一覧、印刷 / PDF 出力
- **技術**: テンプレート（LLM は使わない、または言い換えだけに使う）
- **ROI**: 資料作りの工数がなくなる。発表のスライドにもそのまま使える
- **1日MVP**: 画面を1枚にまとめて印刷用 CSS を当てる
- **リスク**: 単体の価値は低い。最後に30分で足すおまけ機能

## 壁打ちメモ（本当にそれでいい？）

1. **Case 11 の本題は「着陸地点 × 日付 × 太陽・地球の位置」です。** ルート計画だけに寄せると、「課題への適合」で減点されるおそれがあります。**案4（ルート上の太陽・地球）と案3（ルート込みで着陸地点を選ぶ）で本題につなぎ直す**のが必須です。
2. **ルート計画そのものが主題なのは Case 10（火星 EVA ルート）です。** 「移動効率・地形リスク・科学的価値」を正面から問う課題なら Case 10 の方が素直に合います。ただし火星の HiRISE DTM はデータが重く、1日では Case 11（LOLA + PGDA の既製マップ）の方が現実的です。Case 11 を選ぶなら、「着陸地点選びの延長としてのルート」という位置づけで発表してください。
3. **「科学的価値」の点数は自分たちで決めた指標です。** PSR への距離、Diviner の温度、LEND の水素量の**組み合わせ方と重みを画面に明記**してください。根拠を見せないと、科学妥当性で突かれます。
4. **ML を使わない判断は正しいです。** A* とコストの内訳は全部説明できるので、「なぜそのルートか」を説明するという要件と相性が良いです。発表でも「説明できることを優先して、あえて ML を使わなかった」と言い切れます。
5. **最大のリスクはデータの準備です。** 南極の DEM は大きいので、**最初の1〜2時間で「1地域を切り出して傾斜を出す」まで通す**ことを最初のマイルストーンにしてください。PGDA の日照マップが取れなければ、案4は Horizons + DEM の地平線計算だけで作る代替案に切り替えます。
