# Case 14: Space Mission Design Game — アプリ提案

> **テーマ要約**: ミッション目標、探査機の設計、観測機器、ロケット、軌道、予算・質量・電力・通信・データ・ミッション期間などの制約を扱い、**宇宙ミッションを「構想から運用まで」設計・管理・シミュレーションできるゲーム**をつくる。
> **重要ポイント**: ①すべての設計判断に結果（コスト）がある ②正解は1つではない ③1人プレイと最大4人のチームプレイ（役割分担・交渉） ④シミュレーションと評価、「なぜ成功 / 失敗したか」の振り返り ⑤専門知識がなくても遊べる（用語はゲーム内で説明）
> **管理する資源**: 質量、電力、予算、データ、通信、時間（開発期間・運用期間）

---

## 案1: Mission Architect — カードを組み合わせて探査機を作る協力型デッキ構築ゲーム

- **コンセプト**: 探査機の部品（電源、バッテリー、通信アンテナ、コンピューター、姿勢制御、観測機器）を**カード**として扱い、限られた予算でデッキ（探査機）を組む。カードには質量・電力・コスト・データ量・科学価値が書かれ、組み合わせると全体の数値がリアルタイムで変わる。最大4人が役割（ミッション責任者、探査機エンジニア、科学者、通信担当）ごとにカードを出し合う。
- **主な機能**
  - フェーズ: ①目標選択 → ②要求定義 → ③探査機設計 → ④ロケット・軌道選択 → ⑤打ち上げ・運用シミュレーション → ⑥評価
  - 資源メーター（質量 / 電力 / 予算 / データ / 通信 / 時間）が常に表示され、超過すると赤く光る
  - ロケットの能力チェック（「この質量はこのロケットでこの軌道に運べない」）
  - 役割ごとに違う「個人目標」（科学者は科学価値を最大化したい、予算担当は節約したい）→ 交渉が発生
  - ミッションレポート（成功度、科学価値、資源効率、チームワークのスコア）
- **使用データ**: 実在ミッションの公開値を参考にした部品・ロケットのパラメータ（実在の名前は使わず「中型ロケット」等に一般化してもよい）
- **技術スタック例**: React + Socket.io（リアルタイム協力）、Node.js、ゲーム状態は JSON
- **差別化ポイント**: カードという身近な形式で、**判断の結果がすぐ数値に反映される**。課題の主要要件（設計・資源・4人協力・評価）を網羅
- **MVP範囲（2日）**: ミッション3種（地球観測、月周回、小惑星）、部品カード30枚、ロケット3種、軌道3種
- **リスク・注意点**: パラメータが多すぎると難しくなる。初級は資源3つ（質量・電力・予算）に絞る難易度設定を用意

## 案2: Orbit & Coverage Simulator — 軌道を選ぶと「何が見えるか・いつ通信できるか」がわかる

- **コンセプト**: 軌道選択の影響に焦点を当てたシミュレーション中心のゲーム。地球観測ミッションで、軌道の高さ・傾き（低軌道、太陽同期軌道、静止軌道など）を選ぶと、**地球を回る衛星の地上軌跡、観測できる範囲、地上局と通信できる時間**が3D地球儀上で表示される。
- **主な機能**
  - 3D地球儀での軌道・地上軌跡の表示（早送り）
  - 観測目標（例: 日本全土を毎日撮影）の達成度
  - 地上局との通信可能時間 → 送れるデータ量 → 観測機器のデータ量との比較
  - 軌道高度とミッション寿命（大気抵抗による高度低下）のトレードオフ
  - 打ち上げロケットの能力（高い軌道ほど運べる質量が減る）
- **使用データ**: 軌道力学の基本式（ケプラー運動）、地上局の位置（NASA Near Space Network の公開情報など）
- **技術スタック例**: CesiumJS（3D地球）、satellite.js（軌道伝播）、React
- **差別化ポイント**: 課題文の「軌道が観測機会・通信・寿命にどう影響するか」を視覚的に体験できる
- **MVP範囲（2日）**: 軌道4種、地上局3か所、観測目標2種
- **リスク・注意点**: 軌道計算は簡略モデルでよいが、「簡略化している」と明示

## 案3: Mission Control Crisis — 打ち上げ後のトラブルにチームで対応する運用ゲーム

- **コンセプト**: 設計だけでなく「運用」に重点。設計した探査機を打ち上げた後、**ランダムなトラブル**（太陽電池の劣化、通信アンテナの故障、宇宙天気、予算削減、観測目標の追加）が起き、4人のチームが限られた時間で対応を決める。設計時の余裕（マージン）がここで効いてくる。
- **主な機能**
  - リアルタイム運用ダッシュボード（資源の消費を可視化）
  - ランダムイベント（課題文の「予期しない制約」）
  - 役割ごとの操作パネル（電力担当は機器のON/OFF、通信担当は送信スケジュール）
  - 「設計時に◯◯の余裕を持たせていれば防げた」という振り返り
- **使用データ**: 実際のミッションで起きたトラブルの事例（公開情報）をイベントの元ネタに
- **技術スタック例**: Phaser.js / React、Firebase（リアルタイム同期）
- **差別化ポイント**: 「設計 → 運用」の一連の流れを通して、**マージン設計の大切さ**を体験的に学べる
- **MVP範囲（2日）**: 簡易な設計画面 + 運用フェーズ（イベント10種）
- **リスク・注意点**: 運用が楽しすぎて設計が軽視されないよう、設計の判断が運用に効く仕組みを強くする

## 案4: Mission Pitch Battle — チーム対抗で同じ目標のミッションを設計し、成果を競う

- **コンセプト**: 課題文の「競争シナリオ（異なるチームが同じ目標のミッションを設計）」を中心にした教室向けゲーム。各チームが同じ目標（例: 「火星の水を調べよ」）で設計し、シミュレーション結果と、**他チームとの設計の違い**を比較発表する。「正解は1つではない」ことを実感できる。
- **主な機能**
  - 複数チームの同時プレイ（各チーム最大4人）
  - 設計の比較画面（チームA は大型・高コスト、チームB は小型・低コストなど）
  - 評価軸の多様化（科学価値、コスト効率、リスクの低さ）で、どの設計も何かの部門で勝てる
  - 先生用の管理画面（シナリオ設定、結果の一覧表示）
  - 設計の保存・共有（URL）
- **使用データ**: 案1と同様の部品・ロケットパラメータ
- **技術スタック例**: Next.js、Supabase（チーム・ルーム管理）
- **差別化ポイント**: 授業・イベントで使いやすく、普及のストーリーが描ける
- **MVP範囲（2日）**: 2チーム対抗、シナリオ2種、比較画面
- **リスク・注意点**: 単体のゲーム体験が薄くならないよう、設計部分は案1レベルを確保

## 案5: Sandbox Spacecraft Builder — 3Dで探査機を組み立てる自由設計モード

- **コンセプト**: 部品を3D空間でドラッグして組み立てると、質量・重心・電力・コストが即座に計算される「サンドボックス」。太陽電池パネルの向きで発電量が変わる、アンテナの大きさで通信速度が変わる、など**見た目と性能がつながる**ことを体験できる。完成したら簡易シミュレーションで飛ばしてみる。
- **主な機能**
  - 3D組み立て（部品のスナップ配置）
  - リアルタイムの性能表示（質量・電力・データレート・コスト）
  - 「なぜこの性能？」の解説（例: アンテナの直径を2倍にすると通信速度は約4倍）
  - 制約なしのサンドボックスモードと、制約ありのチャレンジモード
  - 設計図の保存・共有
- **使用データ**: 部品パラメータ（公開資料を参考に簡略化）、NASA 3D Resources の部品モデル
- **技術スタック例**: Three.js / React Three Fiber
- **差別化ポイント**: 課題文の「インタラクティブな探査機の可視化」「サンドボックスモード」を実現。デモで目を引く
- **MVP範囲（2日）**: 部品10種の3D組み立て + 性能計算
- **リスク・注意点**: 3D操作の実装に時間を取られやすい。チームプレイ要素は案1と組み合わせる
